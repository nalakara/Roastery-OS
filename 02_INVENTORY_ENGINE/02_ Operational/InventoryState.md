# Inventory State

## Purpose

This document defines the inventory state philosophy and operational inventory state behavior used across Roastery OS.

The purpose of Inventory State is to:
- represent operational inventory condition,
- define inventory readiness,
- preserve workflow clarity,
- support operational traceability,
- and maintain deterministic inventory behavior.

Inventory state is not merely a status label.

Inventory state represents operational reality.

---

# Core Philosophy

Roastery OS treats inventory as:
- evolving operational material,
- production-stage inventory,
- and traceable workflow state.

Inventory state should communicate:
- where inventory currently exists operationally,
- how inventory may be used,
- and what operational condition it currently represents.

The system should prioritize:
- operational clarity,
- deterministic behavior,
- and production-oriented workflow visibility.

---

# Inventory State Philosophy

Inventory is not static.

Inventory continuously evolves through:
- procurement,
- transformation (roasting, blending, extraction, grinding),
- packaging,
- and commercial sales workflows.

Roastery OS separates inventory state into two orthogonal, synchronized dimensions:

```text
1. PHYSICAL OPERATIONAL STATE (What form does the physical material possess?)
   ├── Raw Material (Green Coffee, Ingredients, Raw Packaging)
   ├── Intermediate / Transformed (Roasted Whole Bean, Ground Coffee, Cold Brew Concentrate)
   └── Packaged / Formatted (250g Valve Pouches, 10g Drip Sachets, 1L Glass Bottles)

2. OPERATIONAL AVAILABILITY STATUS (How may this physical stock currently be allocated?)
   ├── Available (Ready for production transformation or sales fulfillment)
   ├── Reserved (Committed to a scheduled batch or customer order)
   ├── In-Transformation (Currently being processed in an active batch)
   ├── Sold / Fulfilled (Deducted via sales transaction)
   ├── Depleted (Zero balance reached)
   └── Archived / Expired (Removed from active operations, preserved for audit)
```

# Commercial Readiness as a Contextual State

*Architectural Refinement:*
In Roastery OS, "Finished Goods" is not a separate physical warehouse silo or immutable database entity.

**Commercial readiness is a contextual role:**
- An `InventoryLot` is commercially ready for a specific `SKU` when its physical state, material, and packaging format satisfy that SKU's fulfillment criteria.
- The same physical lot of roasted coffee held in a storage bin can simultaneously be:
  - available for immediate wholesale fulfillment in bulk containers,
  - available as input for a retail bagging run,
  - available as input for an espresso bar grinding run,
  - or available for a 16-hour cold extraction brew.
- If a packaged product (e.g., 1kg bags) needs to be repurposed into a cold brew run, it does not violate inventory integrity; an explicit `Transformation` consumes the packaged lot, records the decanting/unbagging process, and creates a new intermediate lot.

# State Transition Philosophy

Inventory state transitions occur exclusively through deterministic operational events:

```text
Purchase Receipt Event ──► Creates Raw Material Lot (Status: Available)
                                    │
    ┌───────────────────────────────┴───────────────────────────────┐
    ▼                                                               ▼
Transformation Started (Roasting)                         Direct Wholesale Sale
[Status: Available ──► In-Transformation]                 [Status: Available ──► Sold]
    │
    ▼
Transformation Completed
[Creates Intermediate Lot, Status: Available]
    │
    ├──► Transformation (Grind & Portion) ──► Creates Packaged Lot (Status: Available)
    │                                                    │
    │                                                    ├──► Retail POS Sale [Status: Sold]
    │                                                    └──► Kitting Transformation [Consumed]
    └──► Transformation (Liquid Extraction) ──► Creates Liquid Intermediate Lot
```

### Deterministic State Principles
1. **No Silent State Changes:** Every change of physical state or availability status must be generated by an explicit `Transformation`, `InventoryMovement`, `SalesTransaction`, or `AdjustmentRecord`.
2. **State and Unit Valuation Synchronization:** Physical state changes occurring inside transformations recalculate unit cost based on measured yield loss and added conversion costs.
3. **Traceability Preservation:** Historical states are preserved in the event ledger, ensuring complete genealogical auditability.

Deterministic State Principle
Critical inventory states must remain deterministic.
State changes should:
	•	be event-driven,
	•	remain traceable,
	•	and produce predictable workflow outcomes.
Inventory states should never change silently.
Every meaningful state transition should:
	•	generate operational history,
	•	preserve timestamps,
	•	and remain auditable.

Traceability Principle
Inventory states should preserve operational lineage.
Example:
GreenBeanInventory
Available
↓ roasting
RoastedCoffeeInventory
Available
↓ packaging
FinishedGoodsInventory
Ready For Sale
State evolution should remain:
	•	readable,
	•	explainable,
	•	and operationally meaningful.

Reserved Inventory Philosophy
Reserved inventory represents operational commitment.
Examples:
Reserved for Roast Batch
Reserved for Wholesale Order
Reserved for Packaging
Reserved inventory should:
	•	remain visible,
	•	preserve operational intent,
	•	and reduce accidental inventory conflicts.
The MVP should keep reservation logic lightweight.

Expired and Archived Philosophy
Some inventory may become:
	•	expired,
	•	inactive,
	•	or historically archived.
Example:
Expired Cold Brew
Archived Production Batch
Expired and archived inventory should:
	•	preserve historical traceability,
	•	remain operationally visible,
	•	but no longer participate in active workflows.

Human-Centered Philosophy
Inventory states should remain understandable by operational users.
Operators should quickly understand:
	•	inventory condition,
	•	production readiness,
	•	and operational availability  without requiring ERP-level training.
Operational clarity should take priority over theoretical workflow perfection.

AI Boundary Philosophy
AI systems may:
	•	analyze inventory state behavior,
	•	identify operational bottlenecks,
	•	and recommend optimization opportunities.
However:  AI must not autonomously manipulate critical inventory states.
State transitions must remain:
	•	explicit,
	•	traceable,
	•	deterministic,
	•	and human-auditable.

MVP Scope
The MVP Inventory State system should prioritize:
	•	simple operational states,
	•	deterministic state transitions,
	•	production-oriented workflow visibility,
	•	and inventory clarity.
The MVP intentionally excludes:
	•	enterprise warehouse orchestration,
	•	advanced routing logic,
	•	automated state automation,
	•	and industrial inventory lifecycle complexity.

Architectural Notes
Inventory State is one of the foundational behavioral layers within the Inventory Engine.
Inventory states influence:
	•	workflow behavior,
	•	operational availability,
	•	production readiness,
	•	and traceability visibility.
Inventory states should remain:
	•	modular,
	•	deterministic,
	•	operationally meaningful,
	•	and production-oriented.
Future systems should extend state behavior without redesigning the operational foundation.

Long-Term Direction
The Inventory State system is designed to support future evolution toward:
	•	production orchestration,
	•	warehouse management,
	•	automated workflow visibility,
	•	forecasting systems,
	•	and AI-assisted operational optimization.
However, inventory state behavior should always remain:
	•	understandable,
	•	traceable,
	•	deterministic,
	•	and human-centered.

Philosophy Summary
Inventory state is not merely a label.
Inventory state represents:
	•	operational condition,
	•	production readiness,
	•	and workflow visibility.
Inventory state tells the system:  what inventory currently means operationally.
